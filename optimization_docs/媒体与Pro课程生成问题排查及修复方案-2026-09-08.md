## 3. 为什么 Home 图片／视频开关打不开，Pro 也不能调用

### 3.1 Home 的两级开关形成了无法从界面解除的拦截

当前有两种不同状态：提供商是否启用（`imageProvidersConfig[id].enabled` 等），以及本次是否生成媒体（`imageGenerationEnabled` / `videoGenerationEnabled`）。它们又与“设置面板正在查看的提供商”“实际生成所选 provider/model”“API 测试结果”分别保存。

调用链如下：

```text
内置 provider 默认 enabled=false
  → 填 Key 只更新 apiKey；测试成功只更新测试状态
  → 内置 provider 没有启用控件（自定义 provider 才有）
  → isMediaProviderUsable 判定不可用
  → Home 总开关 set…Enabled(true) 检查不到可用 provider，直接 return
  → 总开关仍为 false，用户看到“点不开”
```

具体位置：

- `lib/store/settings.ts:558`、`:616`：内置图像／视频配置默认 `enabled:false`。
- `components/settings/image-settings.tsx:119`、`components/settings/video-settings.tsx:83`：输入 Key 只写入 Key。
- 上述两文件约 `:220`、`:184`：带 `onEnabledChange` 的字段区受 `isCustom` 限制，内置项没有入口。
- `lib/store/settings-validation.ts:44`：`enabled === false` 会先于凭据检查返回不可用。
- `lib/media/provider-catalog.ts`：Home 列表和可用性判断共用这道条件。
- `lib/store/settings.ts:1427`、`:1437`：总开关无可用 provider 时静默返回。
- `components/generation/media-popover.tsx`：开关本身没有依靠 `disabled` 属性禁止点击；问题在回调后的状态写入。
- `components/settings/index.tsx`：图片／视频侧栏选择只改变设置面板选中项，没有自动切换实际生成的 provider。修完启用入口后，还需处理实际模型选择，否则可能继续指向旧默认项。

服务端 provider 同步可以合并服务端配置标记，但不能绕过这里显式保存的本地 `enabled:false`。不能以“后台填了 Key”推导出 Home 就可生成。

### 3.2 当前 Pro 失败发生在应用内部，未调用 MiniMax

该会话保存的有效媒体快照如下（已去掉凭据）：

```text
imageEnabled = false       image = null
videoEnabled = false       video = null
ttsEnabled   = true        tts 配置数 = 5，均 enabled=true 且有 Key
```

`lib/workbench/media-config-snapshot-client.ts` 现在已经会收集内置提供商和三个全局开关。这说明上一轮“只收集自定义 provider”的问题已经修复；当前快照忠实地携带了关闭状态。

`lib/server/agent-runtime/generate-image.ts:268` 在 `imageEnabled === false` 时直接返回 `Image generation is unavailable.`，结构化原因为 `provider-disabled`。实际 3 次失败正是这个原因，耗时分别约 3、1、0 毫秒。这不是图片模型生成超时，也没有证据说明 MiniMax 余额或 Key 导致了这 3 次错误。

视频的 `hasConfiguredVideoGeneration`（`generate-video.ts:246`）同样先检查 `videoEnabled`，关闭时能力不可用。本轮没有捕获真实上游视频失败记录；视频结论限定为这层可用性拦截。

图片工具仍被注册给 Agent，加上先准备配图的规划，使 Agent 连续调用必然失败的能力。需要在规划开始前提供准确能力状态和不可用原因，避免反复尝试。

### 3.3 其他已提供 API 是否受影响

这处启用入口问题不只影响 MiniMax。确定性测试覆盖了当前 14 个内置图像／视频 provider：

| 类型 | 受同一默认启用门控影响的 provider ID |
| --- | --- |
| 图像（8） | `seedream`、`openai-image`、`qwen-image`、`nano-banana`、`minimax-image`、`grok-image`、`comfyui-image`、`lemonade` |
| 视频（6） | `seedance`、`kling`、`veo`、`minimax-video`、`grok-video`、`happyhorse` |

测试对每个 provider 使用占位凭据／地址：`enabled:false` 时总开关保持关闭；仅将 provider 启用后即可打开总开关。它证明共享门控缺陷，不代表这些服务都做过网络实测。

自定义 provider 已有启用控件，因此不是完全相同的“无入口”问题；仍须验证其启用、实际 provider/model 选择和快照传递。无 Key 的本地服务仍需有效地址，不能把 `requiresApiKey:false` 当作无条件可用。

## 4. 为什么打开 TTS，Pro 仍说没有音色

### 4.1 不是音色计数、额度或 TTS 总开关的问题

该会话有效快照包含 `minimax-tts` / `speech-2.8-hd` 的 5 个音色：

- `female-yujie`
- `female-shaonv`
- `male-qn-jingying`
- `Chinese (Mandarin)_Warm_Girl`
- `Chinese (Mandarin)_Radio_Host`

这 5 项均已启用、带 Key；`ttsEnabled:true`。快照允许的配置数量上限为 100，本次远未触及上限。

但 `lib/server/agent-runtime/roster-tools.ts` 的 `agentVoiceCatalog` 只枚举 `enabledServerTTSProviderIds()` 并读取服务端凭据。`RosterToolDeps` 没有会话媒体配置参数，`runner.ts` 构造 roster 工具时也没有传入已经加载的 `mediaConfig`。

当前运行部署没有服务端 TTS Key，且没有 `/app/server-providers.yml`。因此 `list_voices` 返回空数组，即使当前用户的会话快照已存在可用音色。实际事件在 21:38:58.890 记录了空结果，随后 roster 保存了 3 个未绑定音色的角色。

同一目录还用于 `set_roster` 的音色合法性校验。**只让 `list_voices` 展示音色还不够；必须同时修改保存校验和合成解析，三者使用同一个有效目录。**

### 4.2 “旁白会走默认合成”实际是什么意思

意思是没有为每位课堂人物指定独立声音，后续旁白合成可能使用默认配置。这不等于“Key 没设置”，也不等于本次已经成功生成了音频。

当前 `course-tools.ts` 的旁白路径会接收 `mediaConfig.tts`；`scene-tts.ts` 在角色没有绑定时会选择 `providerConfigs[0]`。对本次快照而言，可能使用首个会话 MiniMax 音色，而不是必然使用部署环境中的声音。这解释了“旁白可能有声音”和“角色目录为空”为什么能同时发生。

此外，当前 `generate_scene` 主要生成内容和讲解动作，并不在该工具内自动完成 TTS；旁白生成还涉及独立的后续工具／流程。提示文案不能保证尚未执行的合成一定成功。

### 4.3 应如何统一

建立会话级有效音色目录，输入包括用户启用意图、已授权的媒体快照、适用的服务端配置和当前会话已注册的克隆音色。输出只向 Agent 提供 provider/model/voice ID、名称、语言等非敏感元数据。

`list_voices`、`set_roster` 校验、实际 TTS 解析都消费同一份目录和配置映射，遵守会话所属用户和凭据引用的权限。已禁用／已撤销配置不能继续使用，不能给 Agent 列出当前请求根本无法合成的声音。

此缺陷也会影响依赖用户会话 Key 的其他 TTS provider，不应只为 MiniMax 写特殊分支。保留原有能力边界：浏览器原生音色不能直接宣称可由服务端 worker 合成；Qwen 当前的 `excludeFromAgentVoiceCatalog` 策略不能为了修 MiniMax 就全局删除；自定义和克隆音色应分别覆盖原有验证规则。

截图中的“锁定页面”也不是数据库锁等待的证据。当前只能确认它处于写页面工具的运行状态，没有捕获 SQL 死锁或锁等待数据。

### 5.2 显式关闭思考存在两处问题，必须分别处理

实际会话模型配置为：

```text
modelString = deepseek:deepseek-v4-flash
thinkingConfig = { mode: disabled, effort: none }
有用户 Key；运行环境 MODEL_ROUTES 未配置覆盖
```

**已确定的问题 A：Pro driver 改写了用户偏好。**

`lib/server/agent-runtime/agent-driver-model.ts:109–118` 原意是去掉工具驱动不支持的 effort 参数，但只要存在 `effort`，或模型属于 effort 控制，就把整个配置改为 `{ mode:'default' }`。因此显式的 `disabled + none` 被改成默认思考行为。确定性测试已复现。

修复应按模型／协议能力删除不支持的字段，同时保留明确关闭思考的语义；不能用“删 effort”作为把整个偏好重置为 default 的理由。服务端明确配置的阶段路由仍需保持既有优先级。

**问题 B：内层生成的异步上下文可能被不同模块副本覆盖。机制已复现，但尚未捕获本次真实发出请求的报文。**

内层 `generation-tools.ts` 使用原始 `deps.modelContext` 创建生成调用，并非复用 driver 改写后的 connection。因此，不能把问题 A 直接当作单页 31,343 reasoning tokens 的完整解释。

内层路径是 `generation-ai-call.ts` → `callLLM` → provider fetch：

- `lib/ai/thinking-context.ts:18` 每次模块加载都创建新的 `AsyncLocalStorage`，随后无条件覆盖 `globalThis.__thinkingContext`。
- `lib/ai/llm.ts` 使用它所导入的实例执行 `.run(thinkingConfig, …)`。
- `lib/ai/providers.ts:2108` 等兼容请求封装从全局实例调用 `.getStore()`。
- 如果模块副本 A 执行 `.run()`，后来模块副本 B 覆盖了全局引用，fetch 读取的是 B，得到 `undefined`，可能无法注入关闭思考的请求字段。

隔离模块重复加载的测试已稳定复现此错位。运行容器的生产 `.next/server/chunks/1785.js`、`9557.js` 均包含相应上下文初始化代码，另有读取方分块，说明生产构建存在需要验证的多副本条件。仅凭代码分块不能证明本次真实请求恰好命中了这种加载顺序。

建议改为同一 Node 全局中的稳定 ALS 单例（全局缓存或 `Symbol.for` 等），导出实例和 fetch 读取实例必须相同，后续模块加载不能覆盖已有实例。`providers.ts` 有客户端使用链，不应直接引入 `node:async_hooks` 破坏客户端构建。也不能用一个普通全局变量保存每个请求的偏好，否则并发用户会串配置。

必须增加生产构建级 mock 上游验证：分别先加载 instrumentation、先访问 API，再并发执行 enabled／disabled 两种请求，核验最终请求里的思考参数及跨请求隔离。只记录脱敏的控制字段，禁止记录 Key、完整私密提示词。以这个测试确认内层机制后再宣称问题 B 已闭环。

另外，`generation-ai-call.ts:38` 使用模型完整 `outputWindow` 作为单次输出上限；当前本地模型目录给该模型配置为 393,216。它不是本次卡住的独立证明，但不能把模型最大容量当作每页合理输出预算。建议增加可配置的阶段预算、截断检测及可恢复错误，基于真实课程验收确定数值，避免粗暴设置过小上限造成 JSON 截断。

### 5.3 生成工作和 UI 进度之间缺少检查点

`generate_scene` 依次执行内容生成、讲解动作生成，完成后才组装、持久化页面并发 checkpoint。昂贵的内容生成已经结束，而后续步骤未完成或被取消时，当前页面仍然没有可恢复的已保存中间状态。

`generation-ai-call.ts` 使用非流式调用；工具内部没有分阶段进度更新。本次只有角色设置产生的检查点，第一页没有中间更新，所以用户几分钟只看到同一状态。

该工具不是完全没有超时：`lib/agent/runtime/tool-timeout.ts` 对 `generate_scene` / `generate_actions` 有 15 分钟覆盖值。本次约 5 分钟后以取消结束，不是触发这个超时。下一轮不应把此次结论写成“15 分钟超时导致失败”，也不应单纯延长超时。

应在内容、动作、TTS、媒体各阶段保存明确进度和可复用产物，UI 展示阶段、页码、已耗时和最近更新。注意 `runner.ts` 的日志瘦身会移除 `tool_execution_update.partialResult`，新增进度要有独立的、安全的持久化字段，不能只向前端流发出一次。

OPENMAIC_AGENT_RUNTIME_ENABLED=true
PARALLEL_SCENE_CONCURRENCY=2
GENERATION_LLM_MAX_INFLIGHT=3

数据库已经存在 Generation Job 相关表，但 `generation_jobs`、`generation_worker_heartbeats` 均无记录。配置里有 worker 并发数，不代表 worker 已启动。

### 6.2 三条现有路径

| 路径 | 当前入口／执行方式 | 持久化与关闭页面 |
| --- | --- | --- |
| 普通模式、后台开关关闭 | `GenerationSessionController.tsx` 探测能力后走前端编排的 API 调用 | 数据可保存到服务端，但前端编排不等于独立 Job；关闭页面不能据此保证继续完成 |
| 普通模式、后台开关开启 | 服务端 Generation Job + `workers/generation/main.ts` | 现有 Job、租约、检查点机制是统一整课生成的基础；当前部署没有启用 |
| Pro | `instrumentation.ts` 在 Next Web 进程启动 `startAgentRunner`；Agent 分多轮调用工具 | 已有 `agent_sessions`、事件和租约恢复，不是纯前端执行；但不是独立 Generation worker，也不与普通模式共用整课 Job |

Pro 关闭标签页主要中断观察连接，不能说它必然立即停止生成；用户显式取消、运行时终止、租约／恢复情况仍需区分。当前 Pro 持久化有价值，应复用会话机制，而不是重复造一套聊天存储。

`lib/agent/runtime/build-agent.ts` 配置工具顺序执行。Pro 多轮规划、读技能、创建角色和逐页工具调度都有额外开销，不能假设它与普通整课流水线执行相同逻辑。不要直接把所有 Agent 工具改为并行，写同一课堂／页面的操作需要有序和互斥。

### 6.3 只改环境变量仍不满足需求

Job 开关由 `lib/server/generation-jobs/config.ts` 判断，只有字符串 `1` 才启用。即便打开并启动 worker，仍有两个代码缺口：

1. Pro 目前不会把整课生成提交给该 Job 系统，仍在自己的工具调用中逐页生成。
2. `lib/generation/session-input.ts` 的后台输入仍拒绝前端用户 LLM 凭据；`generation-jobs/preflight.ts` 仍检查服务端托管模型配置。媒体快照已接入不代表用户模型 Key 也已接入。当前 Pro 用的是用户配置模型，直接切换可能变成预检拒绝。

因此不能把“打开开关＋启动 worker”写成完整修复。

### P1：让两种模式的整课生成真正共用 Job

目标结构（图中提交工具名称是建议新增接口，不是现有实现）：

```text
普通 Home：整理生成输入 ──────────────┐
                                      ├→ 创建同一种 Generation Job（PostgreSQL）
Pro：交互规划→确认输入→提交整课工具 ──┘       ↓
                                      独立 generation worker
                                             ↓
                            同一 runGenerationPipeline + 检查点／资产存储
                                             ↓
                         普通模式：进度＋可预览    Pro：进度＋结果入口
```

1. **先定义共同输入合同。** 在现有 Generation Job 输入基础上携带已确认需求、材料引用、可复用大纲／角色、技能约束、目标 classroom/stage、模型引用及媒体快照引用。Pro 已创建课堂或编辑已有课堂时，不得再创建第二个空课堂。校验 owner、资源归属和已有页面版本。
2. **补齐用户模型凭据路径。** 复用当前 Pro 的服务端加密 `modelRef`／连接 revision 机制，将引用安全绑定到 Job；worker 以正确 owner 解析，保持托管路由优先级和协议限制。Job、日志、UI 不能明文保存 Key。不能简单删除前端凭据禁止校验后把 Key 塞入普通 Job JSON。同步调整 preflight，让合法的会话模型引用可通过。
3. **复用现有流水线。** `lib/server/generation-pipeline/pipeline.ts` 已提供 research、plan、agents、content/actions、media、TTS 等阶段，以及有界内容并发和顺序提交。扩展它接受已完成规划，而不是让 Pro 再执行另一套逐页生成。保留 Pro 的单页修改工具作为编辑能力，整课构建走 Job。
4. **Pro 提交后快速返回 jobId。** Agent 应结束这次长工具等待，展示持久化的“生成中”状态；不要在一个工具里同步等整课完成。会话保存 jobId↔stageId↔owner 的关系，后续查询、错误说明和结果入口使用该关系。
5. **单一写入者与幂等。** 为会话提交设置稳定幂等键，重复发送／恢复不能生成重复 Job；worker 写课期间与 Pro 编辑工具共享可解释的互斥规则。避免 Agent 和 worker 同时改同一页面。关闭页面、停止当前聊天回复、取消生成 Job 是不同动作，UI 与服务端需要明确传播规则。
6. **可恢复检查点。** 每页内容完成即保存，动作／媒体／TTS 各自带状态和产物引用；重启 worker 后从未完成阶段恢复。外部媒体任务保存任务 ID，不能因断线重复创建收费任务；结果不明的调用先核验状态再决定重试。
7. **两种前端只负责提交和观察。** 普通模式保留预览；Pro 隐藏课程画布，但展示当前阶段、第 N/M 页、耗时、失败原因、重试／取消和完成入口。重新进入通过 Job 状态和事件游标恢复，不重新提交。
8. **保留深度交互的价值。** Pro 仍可在提交前通过多轮对话做规划，在提交后解释进度和修改课程；“共用生成逻辑”并不要求抹掉这些交互。用户的“只是 Pro 不显示画面”应体现为展示层差异，不能成为后台执行缺失的理由。

主要涉及：`lib/generation/session-input.ts`、`lib/server/generation-jobs/{contracts,preflight,config-snapshot}.ts`、既有模型连接／快照模块、`lib/server/generation-pipeline/*`、`workers/generation/main.ts`、Pro 课程工具／runner、普通生成控制器和 Pro Job 展示组件。

### P1-部署：代码完成后再验证运行拓扑

1. 核对 `docker-compose.persistence.yml`、`scripts/generation-compose.ps1` 和实际启动方式，确保 Web 与独立 worker 使用同一构建、数据库、必要的配置解密材料和资产存储。
