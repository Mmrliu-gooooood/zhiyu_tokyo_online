## 2. 容量判断

可以把两门课程并行作为实测目标。课程流程有外部模型调用等待，因此课程并发不等于CPU核数；素材解析、图片处理、JSON处理、本机文件和Web请求又会竞争内存、CPU和I/O。既不能从4核推导只能4门，也不能从5名试用者推导必须5门一起运行。

Supabase官方当前列出Free共享CPU、约0.5GB内存、500MB数据库容量；该内存不属于应用主机的8GB。数据库容量、连接、查询与出网均需单独核算。官方没有给出适用于本项目的“最多同时生成几门课”。来源：[定价](https://supabase.com/pricing)、[Compute and Disk](https://supabase.com/docs/guides/platform/compute-and-disk)。本次查阅了changelog与连接文档，没有通过平台能力变化推导新的应用吞吐承诺。

沿用T1连接预算：Web查询3、Worker查询2、LISTEN合计2、维护/备份1，共8条应用连接起步；这是项目预算，不是Free硬上限。等待模型响应期间不应持有SQL事务/连接；提高任务并发不应机械增加连接池。常驻进程优先直连或IPv4 session pooler，保持LISTEN所需语义。来源：[连接方式](https://supabase.com/docs/guides/database/connecting-to-postgres)、[连接管理](https://supabase.com/docs/guides/database/connection-management)。

建议首轮仍采用一个Generation Worker，课程执行并发在全站统一限制内逐步验证到2；保留课内内容并发2、模型请求3、TTS 2、媒体1作为待验证起点。模型额度须按真实凭据核实，不因服务器升级而自动放大。平台密钥/BYOK均受本机资源准入限制，不同凭据可有不同供应商配额组。

## 3. 当前代码差距（静态核对）

| 位置 | 当前行为 | 实施需要解决的问题 |
| --- | --- | --- |
| `workers/generation/runner.ts` | 按单个进程的active集合限制课程并发 | 多Worker及Pro等入口不能借此声称全站统一限额 |
| `lib/server/generation-jobs/repository.ts` 的claim | 数据库中检查同owner运行任务，候选查询前20条 | 准入原子性、跨入口公平性及不可执行的前排任务不阻挡后方可执行用户 |

| `GenerationSessionController.tsx` 的goBackToHome | 服务端任务只停止页面本地运行/观察，不发cancel | 明确后台继续与取消两个动作；离开浏览器不是可靠的服务端取消信号 |
| 同文件applyBackgroundSnapshot | 多种状态按phase映射，缺少专门的排队说明 | 增加服务端状态与等待原因投影，不能只在固定文案后附“正在生成” |
| repository.cancel / heartbeat | 取消会使租约失效，默认心跳间隔10秒后Worker可发现 | UI区分取消提交中、已确认取消及请求失败；不承诺上游服务立即停算或零费用 |
| repository.retry | 只允许failed/needs_attention；cancelled不可重试 | 不能把“取消”写成可随时续跑的“暂停”；保留已完成内容，重新生成策略需明确 |
| `lib/server/generation-jobs/runtime.ts` | 单个Generation连接池max=8，其他模块另有连接 | T1的全应用8条预算尚需真正实现，不能直接相加默认池大小 |

## 4. 状态显示要求与文案示例

保留用户指定的“构建课程中”，后面追加短状态。完成或终止时改成真实终态标题，不继续显示进行中的文案。

| 事实 | 建议显示 | 边界 |
| --- | --- | --- |
| 当前用户执行位已满 | 构建课程中 · 等待你的上一项任务完成 | 与全站繁忙区分 |
| 全站执行位已满 | 构建课程中 · 排队等待 | 无准确调度模型时不显示虚构名次/剩余分钟 |
| 执行中 | 构建课程中 · 正在解析素材/生成大纲/生成页面/合成语音 | 来自服务端phase与步骤，页数用已完成/总数；并行步骤可择主要阶段 |
| 大纲需人工确认 | 构建课程中 · 等待你确认大纲 | 等待用户不等于后台仍占用重任务执行位 |
| 供应商限流退避 | 构建课程中 · 模型繁忙，等待重试 | 有可信retryAt才能显示倒计时 |
| 浏览器读状态失败 | 构建课程中 · 连接中断，正在重连 | 保留最后状态与更新时间，不把观察失败写成任务失败 |
| Worker/数据库不可用 | 构建课程中 · 服务暂不可用 | 由健康/租约事实推导，不能把未更新直接等同崩溃 |
| 正在提交取消 | 构建课程中 · 正在取消 | 仅收到取消成功才改为“已取消”；失败保留重试入口 |
| 终态 | 课程已生成 / 生成失败 / 生成已取消 / 需要确认处理 | 保留已完成页面；可操作错误原因；不泄露服务端堆栈或凭据 |

首页课程卡片、生成页及课堂应指向同一job/stage，提供返回查看入口。刷新、多标签页、重新登录后读取已有任务，不重复提交；晚到的旧课程事件不能覆盖新课程。等待原因与终态优先于阶段文字，不能根据浏览器计时器假装推进。

## 5. 还需落实的边界建议

1. **两层执行限额原子生效**：同用户及全站检查不能先查再分别写，避免并发请求越限；跨账号、跨进程、普通/Pro路径均验收。多步父子工作不重复占位，避免父任务占满后等待子任务死锁。
2. **等待与执行位分开**：排队、等待审阅、长退避和需人工处理建议释放重任务执行位；审阅后重新准入，不能越过正在排队的人。未知外部调用的供应商槽须按既有隔离规则处理，不为快放位而允许无限未知请求。
3. **公平调度与有界积压**：可运行用户之间按等待先后调度，跳过被个人额度阻挡的任务；父任务多个阶段重新排队时保留公平性。纯队列额度和全部未结束任务额度需要分开定义，避免长期审阅积压无限增长。
4. **取消、保留与费用**：推荐保留已完成课程内容；未发出的调用不再启动，未消耗的预占释放；上游已执行调用按证据结算。取消不是暂停，不承诺恢复原任务；删除课程须取消关联作业并拒绝迟到写回。
5. **异常恢复**：Worker退出/重启、断库、请求超时、取消竞态、重复点击与刷新均有确定状态。已确认失败可有界重试，外部结果未知的付费调用不能盲目重放。
6. **任务复杂度边界**：除并发和已有50MB上传限制，还需为素材页数/展开大小、课程页面数、图片/视频数量、TTS文本量、执行时长和模型调用预算建立集中上限；数值以真实试用课程核实，不能默默截断用户需求。
7. **Free与主机保护**：按原计划使媒体字节留在本机文件层，限制事件与状态轮询载荷，保留必要的账本和恢复信息；连接池总预算、数据库容量/出网、临时盘、内存、Web浏览余量分别监控。

其中统一准入、父子任务、身份、账本、备份和Free保护已在主计划存在；本节是在课程体验中补齐验收细节，并非全部属于新需求。
