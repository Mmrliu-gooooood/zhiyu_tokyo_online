# localhost:3000 白屏原因排查与解决方案

排查日期：2026-09-09，Asia/Shanghai。运行证据采集时间约 11:15–11:24。

关联任务：修复媒体与Pro课程生成链路（`01a08161-ebda-7501-82f1-eb16655f162f`）。已读取其记录，但以下根因以本次浏览器复现、在线静态资源和工作区代码为依据。

## 1. 结论

**已确认根因：为恢复异步媒体任务而新增的 Node.js `AsyncLocalStorage` 被打包进浏览器共享模块，首页加载时执行其顶层初始化，导致客户端崩溃。**

故障代码位于 `lib/media/polled-task.ts:2` 和 `:13`：

```ts
import { AsyncLocalStorage } from 'node:async_hooks';

const persistenceContext =
  (globalState.__openmaicPolledTaskPersistence ??=
    new AsyncLocalStorage<PolledTaskPersistence>());
```

当前浏览器实际错误：

```text
TypeError: n.AsyncLocalStorage is not a constructor
```

这次白屏发生在客户端模块初始化阶段。首页 HTTP 已返回 200，Web 容器在监听端口，数据库及 worker readiness 也通过；这些检查不能证明浏览器能够正常显示界面。

本次完成排查及解决方案文档，**未修改业务代码、未重新构建或替换容器、未提交 Git；当前运行服务中的缺陷仍待按本方案修复。**

## 3. 代码导入链与回归来源

### 3.1 首页为什么会加载媒体轮询代码

代码中可直接追踪到以下路径：

```text
app/layout.tsx
  -> components/server-providers-init.tsx（use client）
     -> lib/store/settings.ts:44
        -> lib/media/video-providers.ts:12
           -> lib/media/adapters/seedance-adapter.ts:37
              -> lib/media/polled-task.ts:2、13
                 -> node:async_hooks
                 -> 顶层 new AsyncLocalStorage()
```

`settings.ts` 只需要 provider 配置信息，但 `video-providers.ts` 同时包含目录常量与 adapter 导入。浏览器加载目录时也会触发 adapter 依赖中的模块初始化。多个视频 adapter 共用 `runPolledTask`，因此故障不取决于用户选了哪个视频 provider。

还有一条独立的客户端入口：`lib/store/video-render.ts:23` 直接导入 `runPolledTask`。所以仅拆走 `VIDEO_PROVIDERS` 目录不能保证整个应用的客户端依赖安全。

Next.js 将客户端边界下的模块依赖纳入客户端图；服务端专用代码需要保持独立边界。[Next.js 官方说明](https://nextjs.org/docs/app/getting-started/server-and-client-components)

### 3.2 为什么构建通过后仍然崩溃

`next.config.ts:62` 会将客户端请求的 `node:` 前缀去掉，`:69` 起又把 Node builtins 的 `resolve.fallback` 设置为 `false`。因此 `node:async_hooks` 被替换成空模块，构建没有因为解析该 builtin 而失败。

空模块不能实现 Node API。运行时执行 `new AsyncLocalStorage()` 仍会报错。`AsyncLocalStorage` 本来属于 Node 的 `node:async_hooks`，负责异步上下文传播。[Node.js 官方说明](https://nodejs.org/api/async_context.html)

这解释了“Docker build / TypeScript / 后端健康检查通过，但首页白屏”的现象。

### 3.3 引入缺陷的提交

执行以下只读比较可看到回归：

```powershell
git diff 4d5ad10 535d242 -- lib/media/polled-task.ts
```

提交 `535d242`（`feat(generation): unify durable course generation`）在原有共享轮询函数中增加了：

- `node:async_hooks` 静态导入与顶层 ALS 单例。
- `withPolledTaskPersistence()` 包装器。
- 读取 `resumeTaskId` 和调用 `persistTaskId()` 的逻辑。

新增功能用于保存已提交的异步 provider taskId，供 worker 恢复后继续轮询，避免重复提交。功能目的需要保留，问题是 Node 上下文的存放位置越过了客户端边界。

本次定位的全局键是 `__openmaicPolledTaskPersistence`，不是 `lib/ai/thinking-context.ts` 使用的 `__thinkingContext`。不能把本次错误误写为“已证明 thinking ALS 请求串扰”。

## 4. 推荐修复方案

### 4.1 P0：把 ALS 实例和 run 包装器移入服务端模块

推荐小范围修复：保留共享 `runPolledTask`，通过只读接口读取当前任务上下文；只有服务端模块负责构造 ALS 和执行 `run()`。

| 文件 | 计划调整 |
| --- | --- |
| 新增 `lib/media/polled-task-context.ts` | 仅包含上下文类型与只读 accessor，无 Node 导入或 ALS 实例化 |
| 新增 `lib/server/generation-jobs/polled-task-persistence.ts` | 持有进程级 ALS 单例，导出 `withPolledTaskPersistence` |
| `lib/media/polled-task.ts` | 移除 Node import、ALS 构造和服务端 wrapper；每次运行时调用只读 accessor |
| `lib/server/generation-pipeline/execution.ts:10` | 将 wrapper 导入改指向新服务端文件，保留 `:189` 附近的 taskId 恢复/写入逻辑 |
| `tests/media/polled-task.test.ts` | wrapper 改从服务端导入，原共享函数仍从原文件导入 |
| 新增客户端加载及服务端并发回归测试 | 覆盖下面第 5 节验收行为 |

以下是设计示意，尚未应用到代码中。

共享模块：

```ts
// lib/media/polled-task-context.ts
export interface PolledTaskPersistence {
  resumeTaskId?: string;
  persistTaskId(taskId: string): Promise<void>;
}

interface PersistenceReader {
  getStore(): PolledTaskPersistence | undefined;
}

export function readPolledTaskPersistence(): PolledTaskPersistence | undefined {
  const state = globalThis as typeof globalThis & {
    __openmaicPolledTaskPersistence?: PersistenceReader;
  };
  return state.__openmaicPolledTaskPersistence?.getStore();
}
```

服务端模块：

```ts
// lib/server/generation-jobs/polled-task-persistence.ts
import { AsyncLocalStorage } from 'node:async_hooks';
import type { PolledTaskPersistence } from '@/lib/media/polled-task-context';

const state = globalThis as typeof globalThis & {
  __openmaicPolledTaskPersistence?: AsyncLocalStorage<PolledTaskPersistence>;
};
const context =
  (state.__openmaicPolledTaskPersistence ??=
    new AsyncLocalStorage<PolledTaskPersistence>());

export function withPolledTaskPersistence<T>(
  persistence: PolledTaskPersistence,
  work: () => Promise<T>,
): Promise<T> {
  return context.run(persistence, work);
}
```

然后将 `runPolledTask()` 内的 `persistenceContext.getStore()` 改为 `readPolledTaskPersistence()`。若旧位置需要兼容类型导入，可以仅 `export type`；不能从共享模块重新导出服务端 wrapper，否则会重新拉入 Node 依赖。

必须保持以下行为：

1. 浏览器未安装服务端 carrier 时，accessor 返回 `undefined`，普通轮询和视频导出仍可运行。
2. 每次 `runPolledTask()` 调用时读取上下文，不能在模块加载时缓存 `getStore()` 的结果。
3. Web/worker 使用同名进程单例，多个服务端 chunk 不得各自创建不同 carrier。
4. 并行任务分别读取各自的 `resumeTaskId` 和写入回调，不能以普通全局“当前任务变量”替代 ALS。
5. 新 taskId 在开始轮询前持久化；持久化失败继续报错；恢复任务不再次调用 submit；取消和超时传播逻辑保持不变。

服务端文件还应有客户端导入边界检查。若采用 Next 的 `server-only` 标记，需要同时处理 standalone worker 的 Node/esbuild 入口兼容：当前 `scripts/build-generation-worker.mjs` 使用 `packages: 'external'`，不能在未验证情况下加入可能留到 worker 运行时的标记包。

### 4.2 P1：拆分 provider 目录与执行代码

后续将 `IMAGE_PROVIDERS` / `VIDEO_PROVIDERS` 等纯元数据从 adapter 执行入口分离，客户端设置页、store 只导入目录和浏览器安全的校验工具，减少类似依赖污染。

迁移时检查 adapter 对原 provider 文件的反向导入，例如 ComfyUI 对图片尺寸工具及目录的依赖，避免产生循环依赖。此项是结构改进，不能替代 P0：`video-render.ts` 仍需要浏览器安全的共享轮询函数。

### 4.3 不足以解决本次根因的操作

- 重启相同镜像、清理浏览器缓存或删除 `.next` 后以相同代码重建，仍会产出同类故障代码。
- 只给构造器加浏览器分支，仍保留 Node 静态导入，不能建立可靠模块边界；且容易遗漏后续 `getStore()` 调用。
- 直接删除 taskId 持久化/恢复功能会丢失前次修复要求，并可能造成重复提交。
- 将服务端 wrapper 从共享 barrel 再导出，会使拆分失效。
- 整体移除所有 builtin fallback 涉及原 instrumentation 兼容逻辑；应先修复实际依赖链，再对确实禁止进入客户端的模块设置有针对性的构建检查。
